## 1. 现象与证据

Ari 报：基于 2.2.0-972，切到**没有字幕的音轨**后，插件仍旧显示**历史音轨的字幕**。

真机截图（`Screenshot_2026-10-07-16-55-49`）关键信息：

| 位置 | 内容 |
|---|---|
| 底部播放器 | 曲目名 `本編`、进度 **`00:04`**、播放键为暂停态 |
| 状态栏 + 悬浮窗 | 「咦？真是稀客啊，像你這樣的普通人，居然會出現在這種午夜市場」 |

这句话是**上一轨字幕 JSON 的第 2 条**（cue 1）。而**新轨才播到第 4 秒** ——
「新轨的位置 × 旧轨的字幕列表」正是本 bug 的指纹。

诊断包 `LSPosed_20261007_165531.zip`（`_diag_1007/`）里的两条日志铁证：

```
# ① bug 会话（modules_2026-10-07T16_38_45.794223.log，16:38:51~16:55:21）
[Source] >>> track changed          出现次数 = 0     ← 整段里一次换轨都没被上报
[Source] seeded track index=0 ...   出现次数 = 1
[Source] ignored 5->0 (playlist reset, not a track change)

# ② 同一天更早的 5.5 小时（modules_2026-10-07T11_02_25.623544.log）
ignored 56->0 / 75->0 / 98->0 / 100->0 / 144->0 / 114->0 / 36->0 / 20->0 / 113->0 / 5->0  共 11 次
SPURIOUS 判定                                  = 0 次
track decision: NO subtitles (cues were 0)     = 11 次（全部 cues=0）
```

其中 7 次 `N->0` 在 **50~190ms** 内紧跟 `0->Y`（`56->0`→`0->97`、`113->0`→`0->144`…），
其余 2 次（`56->0` / `5->0`）停在 0 上并**随后加载了新作品的字幕 JSON** ——
⇒ **`N->0` 全部伴随真实的「切作品 / 换音轨」，从来没有出现过「空转归零」。**

## 2. 根因（两条，缺一不可）

### 根因一：权威序号门把「序号归零」当列表重置吞掉 ⇒ 换轨根本没上报

`hook/PlayerSourceHook.java` 的 `onTrackIndexFromStatusMap()` 里有一道早退：

```java
if (isListReset(last, idx)) {                 // isListReset = (idx == 0 && last > 1)
    XposedCompat.log(TAG + " ignored " + last + "->" + idx + " (playlist reset, not a track change)");
    return false;
}
```

它的假设是「序号骤然归 0 = 播放列表被重置，不是换轨」。但 **0 号轨是真实音轨**
（截图里就是 `本編`），于是**切到 0 号轨这件事被静默丢弃**：
数据层收不到 `onTrackChanged` ⇒ `cues` 仍是上一轨的列表 ⇒ 新轨从 0 秒起播、
走到几秒时 `computeIndexAtSecondLocked()` 拿旧列表匹配 ⇒ 画出上一轨的句子。

该判据当初要防的两种情况（**进程重建 / 长时间后台**）已被 `INDEX_STALE_MS = 30s`
那条分支独立拦住（超过 30s 没有序号观测 ⇒ 只重种基线、不发通知），**与它无关**。

### 根因二：裁决窗到点后，上一轨的 cue 又能渲染

`data/SubtitleRepository.java` 的 `onTrackChanged()` 在挂起时确实清空了显示层
（`currentSubtitles = new ArrayList<>()`，code 960 的成果）。但这不是终态：

- 挂起靠 `pendingTrackDecision` 让 `getCues()` 返回空 —— **只覆盖裁决窗那一段**；
- 裁决窗到点、新 JSON 仍没到时，旧实现把 `pendingTrackDecision` 放开，且
  **\(cues\) 一个都没删**（防假阴性的初衷）；
- 于是**旧的 cue 列表重新变成可渲染**，`setPlaybackPositionMs()` 恢复扫描 ⇒
  新轨的当前位置再次匹配到上一轨的 cue ⇒ 字幕「复活」。

这就是用户说的「**仍旧**显示」——不是一次闪现，而是十几秒后稳定地挂在上面。

## 3. 改法（4 文件 / +130 −24）

### `hook/PlayerSourceHook.java`

1. **删掉序号门里的归零吞并分支**：序号一变就上报，日志多一个 `(to first track)` 标注。
2. 上报时带 **`indexVerified = true`**；日志加 `[index-gate]` 标记，真机一眼看出走的是哪条路。
3. `notifyTrackChanged()` 增三参重载；**两参重载保留**并委托 `indexVerified=false`
   —— 老信号路径（按方法名挂 `emitTrackChanged` / `previous` 等）继续用旧的假换轨兜底。
4. `isListReset()` 方法**保留**，只服务老信号路径。

### `data/SubtitleRepository.java`

1. 新增字段 **`previousTrackCuesHidden`** —— 把「数据保留」与「可否渲染」分开：
   - `cues` / `subtitleLineSet` **一个都不删**（JSON 晚到仍能立刻自愈）；
   - 但 `getCues()` / `getCurrentSubtitles()` / `findCurrentCueIndex()` 三处一律按「空」返回
     ⇒ 显示层**结构上不可能**再画出上一轨的字幕；
   - **只掐渲染、不动 UI 口径**：不驱动 `shouldShowNoSubtitles()`，
     所以不会把三处 UI 降级成「无字幕」（那是 2.1.3 明令避免的假阴性观感）。
2. 新增字段 **`pendingIndexVerified`** —— 权威序号门来的换轨**跳过**「位置回退 /
   位置一直往前走 ⇒ 疑似假换轨（SPURIOUS）」那两条兜底。理由：序号变了就是播放列表的
   当前项变了，而兜底是为不可靠的老信号写的；在真换轨上误判会**撤销挂起**，
   等于把旧 cue 放回来渲染（bug 原样复现）。真机两份日志里 SPURIOUS **从未触发**，
   佐证它在序号门上本就不参与。
3. 复位点：`loadFromJsonArrayInternal`（新 JSON = 新音轨字幕 ⇒ 解除隔离 + 清标记）；
   SPURIOUS 分支（同一轨、本来没换 ⇒ 解除隔离）。
4. 自证日志三条：
   - `track changed via <where> [index-gate] | ... [973 previous-track cues quarantined]`
   - `[973] previous-track cues released -> new json arrived, rendering restored`
   - `[code 960] soft verdict ... [973 prev-track cues quarantined, not renderable]`

### `DlsiteSoundSubtitleModule.java` / `app/build.gradle`

- 横幅前插 973 段（历史段全保留，逐字符不变）；版本号四处 → 2.2.1 / 973 / `1007.1`。
- **横幅内容只用中文泛称**，不点名任何标识符 / 探针串（铁律 13：横幅会「自己命中自己」）。

## 6. 已知边界与残留风险（如实记录）

- **未覆盖**：`onTrackChanged` 的「刚加载过 JSON（≤3.5s）⇒ 保留 cues」预加载快捷路径
  没动 —— 若某次换轨恰好落在字幕刚加载后 3.5s 内、且目标轨无字幕，理论上仍可能残留。
  真机日志里字幕 JSON 恒在**换轨之后** 0.3~5.5s 到达（`0->2`+321ms、`2->3`+5.4s、`3->4`+5.5s），
  所以这条路径在本 App 的实际时序里基本不会命中；本轮按「最小改动面」不动它。
- **`isListReset` 仍存在**（只服务老信号路径）⇒ 若要做「该串必须消失」的负向探针，请先删方法。
