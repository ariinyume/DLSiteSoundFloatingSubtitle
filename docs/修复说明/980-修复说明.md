## 三、根因

### 3.1 主因：恢复路径只有「等新 JSON」一条

字幕数据（`cues`）的**唯一**恢复入口是 `loadFromJsonArrayInternal`（一次成功的字幕 JSON 加载）。
可是**宿主对同一条轨的字幕响应有缓存**：切走再切回来它**不会重新发请求**，
于是 `Response.Builder.build()` 的钩子不会再被触发 ⇒ 模块永远等不到新 JSON。

而 975 起「软挂起」会在换轨瞬间就 `softNoSubtitles = true` + `previousTrackCuesHidden = true`
（三处 UI 变「无字幕」、旧 cue 一律不渲染）。15s 后软裁决定案 —— **仍然**保留这两个标志。
两者叠加的结果：**数据一条没丢，界面却永久停在「无字幕」。**

> 这正是仓库铁律里那条的同源错误：**「量不到」不等于「不存在」** ——
> 只是这次的「量不到」不是超时，而是**宿主根本不打算再发一次**。

### 3.2 次因：20s 静默窗把「切回去」也当成了横跳

`settleChange` 的静默规则是「同一对值（**含反向**）在 `INDEX_SUPPRESS_MS = 20000ms` 内不再上报」。
它的本意是挡住宿主在两个列表之间规律交替（976 的教训）。但**用户切回去**是同一对值的**反向**，
于是被一起挡掉：真机时间线里 22:23:45 就已经切回，硬生生被压到 22:23:58.746 才放行 ——
白挂了 13.7 秒「无字幕」。

## 四、修法（两处，均为纯增量）

### 4.1 数据层：给 cues 盖「主人印章」

**新增字段** `SubtitleRepository.cuesOwnerIdentity`（`long`，0 = 未知 / cues 已销毁）：

| 时机 | 动作 |
|---|---|
| 一次成功的字幕 JSON 加载（`loadFromJsonArrayInternal`） | **盖章** = 当时的活跃播放列表身份 |
| 硬裁决销毁 cues（`resolvePendingTrack` 的「手上本来就没有 cues」分支） | **清章** = 0 |
| 普通换轨 | **不动** —— cues 没变，主人就没变 |

身份来源：`PlayerSourceHook.onPlaylistStateFromStatusMap` 在每次读到**活跃列表**时
把身份推给数据层（`noteObservedPlaylistIdentity(long)`，只写一个 volatile 字段，
**不触发任何状态变更** —— 宿主会交替读到多个列表实例，拿它直接驱动 UI 会变成抖动源）。

**新增快路径** `SubtitleRepository.tryResumeFromCache(where, newIdentity)`：
在 `onTrackChanged(String, boolean, long)` 的最前面调用，若
`newIdentity != 0 && newIdentity == cuesOwnerIdentity && !cues.isEmpty()`，则：

1. 撤销 `pendingTrackDecision` / `pendingSoftSuspend` / `softNoSubtitles` / `previousTrackCuesHidden`；
2. `pendingToken++` —— **作废**已排队的「裁决 / 提前收窗」任务；
3. 清掉屏上镜像 `currentSubtitles`（内容改由 cue 路径负责）；
4. 按**当前播放进度**重新定位（`computeIndexAtSecondLocked`），下一帧就是正确的那一句；
5. 若窗口是先前被**本模块自动关掉**的（`autoClosedForNoSubtitle`）→ 开回来；
6. `notifyObservers()`。

### 4.2 闸门：20s 静默加一个例外

`settleChange` 里判断「同对（含反向）+ 20s 内」时，先问一句
`SubtitleRepository.getInstance().ownsCuesFor(to)`：

- **是** ⇒ 这不是宿主横跳，而是用户切回了他刚离开的那条轨 —— **没有裁决窗需要保护**，
  立即放行（打 `back to the playlist our cues belong to -> pass through`），
  并**让静默窗失效**（`sNotifiedMs = 0L`）。失效的必要性：否则紧接着的 `7→1` 会被当成
  反向同对再静默 20s，那 20s 里模块会一直渲染**上一份** cues（错内容）。
- **否** ⇒ 行为与本版之前完全一致（照旧打 `suppressed …` 并返回 false）。

> ⚠️ `INDEX_DEBOUNCE_MS = 600`（同候选再次出现下限）与 `INDEX_SUPPRESS_MS = 20000`（静默窗长度）
> **都没有改**。本轮只是给静默加了一个「目标身份是我们自己缓存的主人」的旁路。

### 4.3 身份是怎么算的（沿用 978，未动）

`makeIdentity(trackCount, durationSec, idx) = tc × 10¹² + durMs × 10³ + idx`。
真机上宿主切「作品 / 音轨」时 `currentIndex` 恒为 0，真正变化的是 `(trackCount, duration)`
（`(7, 278.64s)` ↔ `(1, 2834.494s)`）。判别式「该身份 == 我们缓存的主人」因此等价于
「宿主现在这份活跃列表，就是这份字幕行所属的那条轨」。

## 五、安全性论证（为什么不会画错内容）

1. `cuesOwnerIdentity` **只在一次成功的字幕 JSON 加载时**盖章 ⇒
   「身份一致」严格等价于「这份 cue 列表就是这条轨的字幕」，渲染它不可能画错内容。
2. 身份是三元组打包，**跨轨 / 跨作品必变**：跨作品靠前两项（trackCount + duration）区分，
   同一列表内换轨靠第三项（idx）区分。三者全同才是同一条轨。
3. 快路径有三重前置：`newIdentity != 0`（老信号路径给不出身份 ⇒ 直接不走）、
   身份严格相等、`cues` 非空；任一不满足就交回原有流程（行为与本版之前完全一致）。
4. 硬裁决销毁 cues 时**同步清章** ⇒ 不存在「拿空 cues 去恢复」的窗口。
5. 窗口恢复**只恢复本模块自动关掉的**（`autoClosedForNoSubtitle`）——
   用户手动关掉的窗口永远不会被擅自打开（2.1.3 的既定语义）。
6. 静默窗失效是**一次性**的：放行后仍会把本次 `(from,to)` 写进记忆，只是把失效时间戳清零；
   下一次真换轨又会重新起静默窗。

## 七、已知边界（如实记录）

1. `verify_980.py` 只证「东西进了包、且恢复路径真的接上了」，**不证真机行为**。
2. C3 各条证明「调用点存在」，不证明运行时一定走到 —— 要看真机的 `[code 980]` 日志行。
3. 印章机制的安全前提是「同一轨的身份三元组读数稳定」，这由 978 的实测定标负责，本脚本不重复证。
4. **残留风险（低）**：若宿主同时让两份**不同作品**的列表都处于「活跃」状态（`tc>0`、`dur>0`、
   未 halt）并交替读数，理论上会出现「恢复 → 下一拍又挂起」的抖动。
   978 的权威门（幽灵列表 `tc=0` / `haltReason` 有值一律出局）已在真机上把这种情况清掉，
   本轮真机日志里全程**只有一个**活跃列表（`ihc=7b11b5`），故未观察到该现象。
5. 本轮**未碰**：权威门、软挂起、软裁决、`previousTrackCuesHidden` 的语义、去抖两条阈值、
   末字裁切、设置页布局、`debug_log` 开关。
6. 未发 Release、未真机验证。
