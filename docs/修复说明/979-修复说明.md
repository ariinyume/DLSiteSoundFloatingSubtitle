## 一、这些日志是什么

`statusMap via=…` 是 **977/978 加的只读诊断转储**（`PlayerPositionHook.dumpStatusMap`），
用于定位「切到无字幕音轨仍残留」那条 bug：把宿主的整张播放器状态 Map **原样打出来**，
看「模块多久才读到一次状态、从哪个通道读的、是哪个实例」。

它是那两轮排查的**唯一证据来源**，必须留着；但频率很高：

| 因子 | 值 | 常量 |
|---|---|---|
| 兜底轮询节奏 | 每 1 秒（空闲 >15s 降到 3s） | `POLL_INTERVAL_MS=1000` / `POLL_SLOW_INTERVAL_MS=3000` |
| 每轮遍历的实例数 | 最多 6 个 | `MAX_REMEMBERED_PLAYERS=6` |
| 每条日志的节流 | 按「来源 + 实例」各自 2.5 秒一条 | `MAP_DUMP_MIN_INTERVAL_MS=2500` |

⇒ 单个实例约 **每 2.5~3 秒一条**，宿主多实例/多通道时成倍，真机约 **20~70 条/分钟**。

★ 顺带确认：用户贴的那条日志里有 `ihc=`（实例标识）和 `id=099fb317…~`（String 打实际值），
这两处都是 **978 独有的补强** ⇒ 说明机上装的**就是 978**。

## 二、本版改了什么

**只加一个开关，把「诊断级日志」默认关掉；不改任何功能行为。**

| 项 | 内容 |
|---|---|
| 配置键 | `debug_log`（默认 **false**） |
| 设置页位置 | 「其他」卡片 → 「状态栏字幕功能」**下方**、「字幕配置备份与恢复」**上方** |
| 文案 | 标签「调试日志」（繁：偵錯日誌 / 英：Debug log）+ 常驻小字「排查问题时才需要打开，日常保持关闭可减少日志刷屏」 |
| 闸门出口 | `RemoteConfig.debugLog()`（进程内 volatile 读，热路径零成本） |

### 被静音的「诊断级」日志

1. `statusMap via=…` —— 状态 Map 全量转储（977 引入 / 978 补强）。**关闭时整段跳过**，
   连 StringBuilder 拼接与节流表更新都省掉。
2. `poll tick #N players=… idle=…ms` —— 兜底轮询自证（977 引入，每 10s 一条）。
3. `change <from>-><to> suppressed (…)` —— 换轨闸门的**抑制行**（976 引入）。
4. `ignored <where> … (playlist reset …)` / `ignored <where> (track index unchanged=…)`
   —— 换轨老信号路径的两条**忽略行**。

### 仍然常开（里程碑 / 告警，低频）

- 钩子挂载行（`hooked …`）
- 种基线行（`seeded playlist identity …` / `seeded track index=…`，每进程一次）
- ★ **真正的换轨上报** `>>> track changed: …`
- `polling stopped (no sample for …)`（轮询彻底停，状态跃迁）
- **全部 WARN / 错误行**

> 也就是说：关闭（默认）后，日常运行日志只剩「里程碑 + 告警」；
> 一旦要排查，把开关打开，977/978 那套诊断立刻原样回来。

## 三、配置链路（与其它键完全同源）

`SubtitleConfig` 一处加字段 ⇒ 三条通道自动带上：

```
SubtitleConfig.debugLog (boolean, 默认 false)
  ├─ SharedPreferences（MODE_PRIVATE，同步 commit）
  ├─ 标准配置 JSON（原子写）
  └─ ACTION_CONFIG_CHANGED 广播（带完整配置 JSON）→ 被注入进程 RemoteConfig.applyFromJson
                                                        ⇒ 写本进程本地 prefs + 内存生效
```

`debugLog()` 在 hook 侧仅做一次 `RemoteConfig.get()`（volatile 读）⇒ 每次轮询/每次采样调用都可接受。

## 五、已知边界（如实记录）

1. 验证只证「东西进了包 + 闸门接对了线」，**不证真机日志一定安静** —— 那要真机复测。
