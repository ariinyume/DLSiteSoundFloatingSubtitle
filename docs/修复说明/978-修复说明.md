## 一句话结论

**前五版（973/974/975/976/977）全都在调「序号判据」的时序与去抖 —— 但真机上宿主切作品/音轨时，`AudioPlaylist.currentIndex` 恒为 0，序号判据一次都没成立过。** 本轮把判据的根换掉：改用**播放列表身份** `(trackCount, duration, currentIndex)` 三元组。

## 二、根因（两条）

### ① 判据选错了字段（本轮核心）

前五版都在优化「序号判据」的去抖、采样、时序 —— **但被测的字段根本不随切换变化**。

| 版本 | 判据 | 真机结果 |
|---|---|---|
| 973 | 序号变化 + 取消「归零=列表重置」吞并 | 0 次 |
| 974 | 序号变化，一读一变就报 | 每秒 1 次（横跳）→ 裁决被反复作废 |
| 975 | 序号连续稳定 ≥1200ms 才采信 | **0 次**（规律交替下永远攒不满） |
| 976 | 序号首报即报 + 20s 长静默 | 真机仍 0 次 |
| 977 | 同上 + 轮询降频 + 不再重种基线 | 真机仍 **0 次** |
| **978** | **列表身份 `(trackCount, duration, currentIndex)`** | **离线模拟 1 次 ✓** |

**真正随切换变化的是**：`(trackCount, duration)` = `(6, 731.832s) → (1, 2431.085s)`。

### ② 多实例读数互相污染（顺带挖出来的）

宿主**同时持有多个 `AudioPlaylist` 实例**：

- **活跃列表**：`trackCount>0`、`duration>0`、`haltReason=null`（真在播的那份）
- **已停止的幽灵列表**：`trackCount=0`、`haltReason=<有值>`、`currentTime=0.0`、`playing=false`
- **闲置的单曲播放器**：`AudioPlayer` —— `playing=false`、`isLoaded=false`、`currentTime=0.0`

它们的读数**交替流进**同一个 `consume()`，后果：

1. **进度被幽灵实例的 `currentTime=0.0` 反复拉回 0** ⇒ 字幕按旧 cue 列表匹配 ⇒ **渲染出上一轨的句子**（这正是用户看到的现象之一）；
2. **`playing` 每秒横跳 29 次**（日志 `playback resumed` / `playback paused` 交替刷屏）；
3. **`playbackState` 被覆盖** ⇒ 真机 `playback end not confirmed (state came back to 3) -> keep floating window` **出现 47 次** —— 「播放结束自动关窗」这条路径被彻底顶掉。

## 三、修法

| # | 改动 | 文件 |
|---|---|---|
| ① | 判据由 `currentIndex` 升级为 **三元组身份** `(trackCount, durationMs, currentIndex)`，打包成 long 比较。跨作品换列表靠前两项触发，同列表内换轨靠第三项触发 | `PlayerSourceHook.onPlaylistStateFromStatusMap` |
| ② | 新增**权威门**：只有**活跃列表**（`trackCount>0 && duration>0 && haltReason==null`）这一路读数有权更新仓库状态；幽灵列表与闲置 `AudioPlayer` 只贡献诊断 | `PlayerPositionHook.consume` |
| ③ | 诊断补强：`dumpStatusMap` 不再把 String 抹成 `<str>`，改打**实际值**（>24 字符截断）；节流键由 `where` 改为 `where#identityHashCode`，同类多实例不再互相覆盖 | `PlayerPositionHook.dumpStatusMap` |

**★ 976 的两道去抖闸门（`INDEX_DEBOUNCE_MS=600` / `INDEX_SUPPRESS_MS=20000`）一字未动** —— 只是比较对象从 int 序号换成 long 身份。多实例横跳在 978 真机上依然存在，长静默反而更关键。

**老宿主兼容**：宿主从未暴露 `trackCount` 键时，权威门自动放行（退回「全部上报」的旧行为），身份退化为纯序号 ⇒ 老能力不丢。

## 六、双闭环

- **闭环① apply**：`git archive HEAD` 干净树 + 覆盖 11 个改动文件 → 编译 ⇒ **sha == 交付包**（逐字节一致）
- **闭环② revert**：**另一棵**干净树还原成 HEAD → 编译 ⇒ 与交付包**不同**；若等于已发布的 972 包 `6954e891…` ⇒ 顺带证明「本工具链整包可复现」
- ⚠️ **铁律 5b**：两棵树都是**全新抽出**的 ⇒ 天然两边 clean，双闭环才有意义（977 那轮吃过增量构建的假 FAIL）。

## 七、怎么验（真机复测指引）

**装包后**：作品 A（有字幕）→ 作品 B（无字幕），旧字幕应立即清空、悬浮窗应在 **5 秒内**关掉。

**只看这几行日志即可定位**（标签 `[DLsiteSoundFloat]` / `[DLsiteSoundFloat:Source]`）：

1. **修好了** ⇒ 出现
   `[Source] >>> track changed: … playlist tc=6 dur=731832ms idx=0 -> tc=1 dur=2431085ms idx=0 [index-gate]`
   随后跟数据层的换轨裁决日志，5s 内 `floating window hidden`。
2. **还有问题** ⇒ 把 `statusMap via=… ihc=…` 那几行整段抓来。本版已能直接看到
   `id=` / `playbackState=` / `haltReason=` 的**实际值**（977 把这些抹成了 `<str>`，正是上一轮定位卡住的地方），
   以及**同类到底有几个实例**（`ihc=` 不同即不同实例）。
3. 若看到 `playlist … suppressed (same pair within 20000ms …)` ⇒ 宿主在横跳，长静默正在按设计工作，不用管。

## 八、已知边界（如实记录）

1. 静态判据只证「东西进了包」，**不证真机行为** —— 必须真机复测。
2. 诊断转储会显著增加日志量（已按 `where#ihc` 节流到 2.5s）。
3. 「同作品内换音轨」时若 `trackCount`/`duration` **也**不变、只有 `currentIndex` 变 ⇒ 978 同样能触发（身份含 `idx` 分量，D.4 已证）。但若宿主的「音轨」是**独立列表实例且 `currentIndex` 恒 0**（如本轮的作品 A↔B），则靠 `trackCount`/`duration` 区分 —— 两者 `duration` 相同（同一音轨的两个版本）时**仍会漏判**。这种情况下需要靠 `id` 字段，本轮已把 `id` 打出来，下一轮可直接加进身份。
