## 1. §1 插件经常检测不到宿主在运行，持续显示「模块未激活」

### 症状
宿主（DLsiteSound）一直开在后台，设置页状态卡却频繁停在「未激活 / 未运行」。

### 根因（三层叠加，全部有出处）

| # | 根因 | 出处 |
|---|---|---|
| A | **两条探测广播都是隐式广播**。Android 8.0（API 26）起，**后台进程动态注册的 receiver 收不到隐式广播** ⇒ 宿主退到后台后既收不到 PING、也没机会回 PONG | 平台行为 + 源码（`ConfigBus.sendHostScopePing` / `StatusBarSubtitleBridge.sendScopePing` 原来都只 `new Intent(ACTION)` 后 `sendBroadcast`） |
| B | **探测窗只有 1200 ms**，太短。宿主被系统降级/唤醒途中稍有延迟就错过 | `ScopeProbe.DEFAULT_WINDOW_MS = 1200L` |
| C | **没有任何会话内记忆**。一次探测失败就把状态卡打回「未激活」，哪怕上一秒还确认过 | `SettingsActivity.renderStatusCard()` 直接读 `mProbe` |

日志旁证：`19:16:27` 的 PONG 里带 `hostAlive=false`；`19:18:21~19:31:10` 整段宿主连状态 Map 都不再被读（只有 `seeded track index=0 … since=674458ms`）。
同一份日志里还有 `systemui scope -> revoked (heartbeat …)` 与 `authorized` 每 15~30s 交替 ⇒ **SystemUI 心跳也偶发丢包**，同源。

### 改法
1. **两条 PING 改显式广播**（不受后台广播限制，系统可直接投递并唤醒目标进程）：
   - `config/ConfigBus.java`：`ping.setPackage(HOST_PKG)`（`HOST_PKG = "jp.co.eisys.dlsitesound"`，常量本已存在）
   - `util/StatusBarSubtitleBridge.java`：新增 `SYSTEMUI_PKG = "com.android.systemui"`，`ping.setPackage(SYSTEMUI_PKG)`
2. **探测窗 1200 → 2800 ms + 窗口内每 400 ms 重发一轮**（约 7 轮，任一轮收到 PONG 即成功）：
   - `util/ScopeProbe.java`：`DEFAULT_WINDOW_MS = 2800L`、新增 `PING_REPEAT_MS = 400L`、探测主体改成 `pingLoop` 自递归重发
3. **会话内记忆**：`ui/SettingsActivity.java` 新增字段 `mHostSeenOnce`，探到宿主授权就置位；
   `hostAuthorized = !probing && (mProbe.hostAuthorized || mHostSeenOnce)`

> ⚠️ 这条是**本轮唯一没有静态判据能证伪**的改动 —— 广播到底有没有被后台宿主收到，只有真机日志能证。

## 3. §3 卡片最下方文字贴卡片底太紧

### 症状
每张卡片最下方那行提示文字，与卡片底边**贴得很紧**（参考图蓝圈处）。
Ari 要的是：**和「卡片顶边 → 第一个选项文字」的距离一致**（即上下对称）。

### 根因
文本视图的**盒子底**与**字形底**之间天生隔着两段空档：
1. `includeFontPadding`：盒子底取字体包围盒 bottom，比 descent 更低（CJK 约 2dp）；
2. `lineSpacingMultiplier`（Hint 样式 1.15）：倍数余量算进**最后一行**行高（约 2.5dp）。

⇒ 974 设的「盒子底 6dp」在真机观感上是 9~10dp。

### 改法（`ui/SettingsActivity.java`）
`pinCardLastTextInk()` 从「固定 6dp」改为「**与首行字形顶距对称**」：
- 新增 `topInkGapOf(group)`：递归找卡片里**第一个可见 TextView**，量出首行「字形顶」到卡片顶边的距离 = 目标值 `target`；
- 布局完成后量末行「字形底」到卡片底边的当前距离 `curGap`；
- 线性布局里「子 View 的 bottomMargin 增量 = 容器高度增量」，而字形位置不受影响
  ⇒ **应写的 margin = target − curGap**（负值即往下压）；
- 只夹「不要把文字压出卡片下沿」这一侧（宁愿多留白，不能裁字）；
- `includeFontPadding=false` 照旧关掉，行距倍数不动（会影响换行可读性）。

新增辅助：`topInkGapOf` / `findFirstTextView` / `topRelativeTo`。

## 8. §8 从有字幕音轨切到无字幕音轨，仍残留上一轨字幕且不关窗

### 症状
切到没有字幕的音轨后，插件仍显示上一音轨的字幕，悬浮窗也不关。

### 根因（日志铁证）
`x193455/log/modules_2026-10-07T18_21_41.701994.log`：

```
19:17:41.998  >>> track changed: …AudioPlaylist 0->2 [index-gate]
19:17:42.908  >>> track changed: …AudioPlaylist 2->0 (to first track) [index-gate]
19:17:43.909  >>> track changed: …AudioPlaylist 2->0 (to first track) [index-gate]
   …（每秒一条，共 15 条，直到 19:17:56.943）
```

每条后面都跟着一条 `-> SUSPEND subtitles, wait 3000ms [973 previous-track cues quarantined]`。

**机制**：宿主状态 Map 的 `currentIndex` 在切轨期以约 500 ms 为周期在 `0` 与 `2` 之间交替。
旧实现「一读一变就上报」，配合 500 ms 去重窗（`DEDUP_MS`）恰好形成循环：

```
读 0 → 基线 2 变 0 → 上报 2->0（可见）
读 2 → 基线 0 变 2 → 上报被 500ms 去重吞掉（不可见，但基线已被改写）
读 0 → 再上报 2->0（可见）……
```
⇒ 可见日志上「每秒一条 `2->0`」，**连发 15 次**。

每次上报都让数据层的待定裁决**换一个 token**（`pendingToken++`）⇒ 上一次排的
`resolvePendingTrack` 被作废 ⇒ 裁决任务**永远到不了点** ⇒ 字幕永久停在「挂起」、
悬浮窗既不关也不再更新。

### 改法（两层）

**信号层 —— `hook/PlayerSourceHook.java`**（新增「待定 + 稳定化闸门」）
- 新增常量 `INDEX_DEBOUNCE_MS = 1200L`、`INDEX_REPEAT_SUPPRESS_MS = 2000L`；
  新增状态 `sPendingIdx / sPendingSinceMs / sNotifiedFrom / sNotifiedTo / sNotifiedMs`
- 新增 `settleIndexChange(from, idx, now)`：读到的序号与基线不同 ⇒ **先不采信、先记待定**；
  同一候选**连续稳定 ≥ 1200 ms** 才放行；中途读回基线值 ⇒ `clearPendingIndex()` 撤销待定、重新计时
  ⇒ **交替型抖动永远攒不满时长，一次也不会误报**
- 放行后还有一层「同一对 (from→to) 在 2 s 内重复出现则抑制」
- `onTrackIndexFromStatusMap` 与老信号路径 `notifyIfTrackIndexChanged` **共用**这道闸门
- 代价：真换轨的响应多等约 1.2 s（只影响「换轨瞬间」的字幕，可接受）

**数据层 —— `data/SubtitleRepository.java`**
- `onTrackChanged` 的挂起分支新增 `softNoSubtitles = true;`
  ⇒ 换轨**瞬间**就把本音轨按「无字幕」呈现（胶囊 / 状态卡 / 悬浮窗三处口径统一）
- 软挂起**也**排提前收窗（原 973/960 是「软挂起不排」）：
  `mainHandler.postDelayed(() -> provisionalEarlyClose(token), min(5000, grace))`
  ⇒ 5 s 内等不到新 JSON 就关窗
- ⚠️ 不是永久结论：任何一次字幕 JSON 到达都会由 `loadFromJsonArrayInternal` 自动清掉
  `softNoSubtitles` 并把窗口开回来 ⇒ 真机上 JSON 晚到 5.5s / 11.1s 的轨表现为「先空后自动恢复」
- 代价：JSON 晚于 5s 的轨会「先关窗、到了再开回」= 一次轻微窗口闪。
  这是「错误内容一直挂着」与「偶尔闪一下」之间的取舍，**本轮按 Ari 指令选后者**。

## 11. 本轮新增的判据经验（写下一轮验证脚本前必读）

1. 🟢 **查 `static final` 常量 → 直接读 dex 字段的 `value :` 行**（`dexdump -d`），
   不要反汇编数 `const` 立即数。理由：精确（不受方法里无关字面量干扰）、双向（字段不存在 = None）、
   省事（不用挑方法、不怕重载、不怕内联）。本轮 4 组 12 条判据一次全中。
2. 🔴 **`dp()` 是 `(F)I`，吃 float**：设置页的 int 尺寸常量走 `dp(...)` 时被加宽成 float 再进指令
   ⇒ 立即数是 **32.0f 的 IEEE-754 位型 `1107296256`**，不是 `32`。
   同理 48.0f = `1111490560`、16.0f = `1098907648`。按十进制找必然落空。
3. 🔴 **不要断言「某个立即数绝迹」**：`snapToCharBoundary` 里除阈值外还有一处**无关**的立即数 6
   （974/975 都带着）⇒ 「975 里 6 必须绝迹」会**假 FAIL**。只比计数差（旧值 −1、新值 +1）。
   （改用判据经验 1 之后这个坑自然消失 —— 这正是改进的动机。）
4. 🔴 **dexdump 的类描述行有 2 空格缩进**（`  Class descriptor  : 'L…;'`），`startswith` 前必须 `lstrip()`。
5. 🔴 **aapt2 打印 float 尺寸有 float32 精度损失**：XML `7.2dp` → `7.199982dp`、`14.4dp` → `14.399994dp`
   ⇒ 维度判据必须走数值容差；`24dp` 恰可精确表示所以能直接对上。
6. 🔴 **`extract_dex` 的返回值是 APK 内的条目名，不是本地路径**：后续 `dexdump` 必须吃本地路径，
   两者要分开存。本轮把条目名当路径传给 dexdump，导致 12 条判据集体假 FAIL。
