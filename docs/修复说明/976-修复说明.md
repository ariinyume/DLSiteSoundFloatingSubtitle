## 1. §4 根因：**975 把修复方向修反了**（本轮核心）

### 1.1 先确认现场：Ari 测的确实是 975

日志 `modules_2026-10-07T20_12_54` 段（`x201249/log/modules_2026-10-07T19_36_47.879327.log`）里：

```
20:08:48.862  (com.android.systemui) hook() enter, module build=2.2.3 (code 975)
20:10:21.168  (jp.co.eisys.dlsitesound) ==== BUILD 2.2.3 / code 975 （…）
```

⇒ 机上装的就是 975，所以「还是没修复好」是针对 975 的有效反馈。
**而整份日志里换轨事件 `[Source] track changed` 一条都没有**（974 时段是每秒一条）—— 这是最关键的一行证据。

### 1.2 975 的修法为什么把通道**堵死**了

975 的判据是「**新序号连续稳定 ≥ INDEX_DEBOUNCE_MS(1200ms) 才采信**」，并且：
- `onTrackIndexFromStatusMap` 的「读到基线值」分支里调 `clearPendingIndex()` **把候选的计时清零**；
- `notifyIfTrackIndexChanged` 末尾同样是 `clearPendingIndex()`。

而宿主（R8 后的 expo 状态 Map）在切轨期间是**规律交替**：`currentIndex` 每约 1s 在 `0` 与 `2` 之间来回跳。于是：

```
t=0.0s  读到 0（候选，开始计时）
t=1.0s  读到 2（== 基线）⇒ clearPendingIndex()  ← 计时被抹掉
t=2.0s  读到 0（候选，重新开始计时）
t=3.0s  读到 2 ⇒ 又抹掉
   …        永远攒不满 1200ms ⇒ onTrackChanged 一次都发不出去
```

⇒ 数据层**压根不知道换过轨** ⇒ `previousTrackCuesHidden` / `softNoSubtitles` 从未置位 ⇒
**旧字幕继续渲染、悬浮窗继续挂着** —— 正是 Ari 报的现象。
（974 的症状是「裁决被反复作废」，975 改成「根本没有裁决」，**比 974 更糟**。）

### 1.3 离线自证（`tools/sim_jitter.py`，9 PASS / 0 FAIL）

把 Java 判据逐行照搬成 Python，用真机时序（500ms 一拍、0/2 交替、持续 15s）跑：

| 用例 | 975 版 | 976 版 |
|---|---|---|
| **宿主横跳**（本轮现场） | **0 次放行**（复现真机现象） | **恰好 1 次**，t=1500ms |
| 真换轨 2→0 后稳定 | 1 次，t=1500ms | 1 次，**t=900ms（更快）** |
| 2→0 后再切到第三轨 1 | 2 次 | 2 次（第三值能穿透静默窗） |

外加一条**模型自检**：把 976 的静默窗改成 0 ⇒ 横跳用例放行次数变成 **10 次**
⇒ 证明「恰好 1 次」是静默窗挣来的，不是模型恒为 1（防「永远绿灯」的假证据）。

### 1.4 976 的修法：**首报即报 + 长静默**（`hook/PlayerSourceHook.java`）

| 改动 | 975 | 976 |
|---|---|---|
| 读到基线值时 | `clearPendingIndex()` 清零 ❌ | **不清零**（候选计时跨过它继续累积） |
| `INDEX_DEBOUNCE_MS`（同候选两次出现的最小间隔） | 1200ms | **600ms** |
| 同对重复抑制 | `INDEX_REPEAT_SUPPRESS_MS = 2000`（仅同向） | **删除**，改为 `INDEX_SUPPRESS_MS = 20000`（**含反向**，且**第三个序号可穿透**） |

- 静默窗取 20000ms 的理由：**必须 > 数据层裁决窗**（`NO_SUBTITLE_GRACE_MS = 3000ms`）——
  这正是 974「每 500ms 报一次 ⇒ 裁决被反复作废」的根治点；宿主横跳实测约 15s，20s 能全覆盖。
- 第三值穿透：抖动只在 `{0,2}` 两个值之间 ⇒ 全被抑制；用户主动切到第三轨（如 1）⇒ 立即放行，
  不会因为静默窗而吞掉真实的换轨。

**数据层本轮零改动** —— 975 加的两条（换轨瞬间 `softNoSubtitles = true`、
软挂起也排 5s 提前收窗）方向本来就是对的，只是信号送不到。代码复核确认：
- 换轨瞬间：`currentSubtitles` 清空 + `previousTrackCuesHidden = true` + `softNoSubtitles = true`
  ⇒ 胶囊/状态卡/悬浮窗三处立刻按「无字幕」呈现；
- `provisionalEarlyClose` 有 `token != pendingToken || !pendingTrackDecision || !floatingWindowOpen`
  三道卫语句 ⇒ JSON 到了就不会误关，`loadFromJsonArrayInternal` 会清 `softNoSubtitles` 并开回窗口。

## 2. §1 四张卡片最下方内容的底距：再翻一倍

**975 只处理了三张卡。** 复核代码发现：`addResetRow` 末尾调用 `pinCardLastTextInk(parent, hint)`
（hint = 「恢复默认」下方那行小字），而 `buildMiscGroup` 末尾是**导出/导入按钮行**，
**从来没走过这个函数** —— 所以「其他」卡片一直只吃卡片自身 6dp 内距，这就是"还是很紧"的一半原因。

改法（`ui/SettingsActivity.java`）：

- 方法改名 `pinCardLastTextInk` → **`pinCardLastBottom`**，参数类型 `TextView` → **`View`**：
  - **文字**（前三张卡）⇒ 对齐**字形底**（要减掉字体自带下空档）；
  - **容器/按钮行**（「其他」卡）⇒ 对齐**盒底**（按钮自带填充背景，盒底就是视觉底边）。
- 目标值 `target = topInkGapOf(group) × 2`（975 是「与首行字形顶距对称」，本轮再翻一倍）。
- 收敛式不变：`bottomMargin ← target − curGap`，负的一侧仍夹在 `−CARD_PAD_BOTTOM_DP`。

## 4. §5 底部彩蛋（新功能）

**布局**（`activity_settings.xml`，`settings_content` 的最后一个子 View）：

```xml
<TextView
    android:id="@+id/egg_smile"
    android:layout_width="match_parent"
    android:layout_height="wrap_content"
    android:layout_marginTop="6dp"
    android:alpha="0"                 <!-- 占位但不显示 -->
    android:gravity="center"
    android:text="SMILE! :D"
    android:textAppearance="@style/TextAppearance.DLsiteFloat.Hint"
    android:textColor="?attr/colorOnSurfaceVariant" />
```

**代码**（`ui/SettingsActivity.setupScrollEgg()`）：

- **必须用触摸监听，不能用滚动回调** —— 滚到最底之后继续上拉只会走 `NestedScrollView`
  的 EdgeEffect 回弹，**scrollY 一个像素都不再变**，任何基于 scrollY 的判断都看不见这个动作。
- 触发：`已到底 且 上拉 > EGG_PULL_DP(16dp)` ⇒ 淡入；
  手指改为下拉 ⇒ 立刻淡出；松手 ⇒ 延后 `EGG_LINGER_MS(1600ms)` 再淡出（好让用户看清）。
- 淡入淡出 `EGG_FADE_MS = 180ms`。
- **监听器一律 `return false`（不消费事件）** ⇒ 滚动、AppBarLayout 吸顶、预览卡钉住全不受影响。
- `alpha=0` 是**占位**不是隐藏：必须 `VISIBLE` 才有布局高度，用户才滚得到它；
  用 `GONE` 控制会导致「用户根本滚不到彩蛋」。

## 6. 边界 / 待真机确认

1. **§4 无法用静态判据证伪** —— 脚本能证「判据形态已按设计改掉」，
   但「真机上切轨后悬浮窗会不会在 5s 内关掉」只有上机能证。
   **建议复核步骤**：播放有字幕的音轨 → 切到无字幕音轨 → 看
   ① 字幕是否立刻消失（≤1 拍）② 悬浮窗是否在约 5s 内关闭 ③ 抓 `[Source]` 是否有且仅有一条换轨上报。
2. **§4 的静默窗是 20s**：若 20s 内连续切轨且**都是同样两个序号**（例如只有 0/1 两条轨来回切），
   第二次起会被吞。实测宿主横跳就是 `{0,2}` 两个值，所以这个代价是必须付的；
   若真机上觉得「快速连切两条轨时不跟手」，可把 `INDEX_SUPPRESS_MS` 降到 8000ms
   （仍 > 3s 裁决窗，但横跳 15s 的中后段会多报 1 次，表现为窗口关闭晚几秒）。
3. **§1 的「×2」是观感量**：`target = 首行字形顶距 × 2`。按当前度量估算约 30~36dp。
   若真机上觉得过大/过小，改 `pinCardLastBottom` 里的 `* 2` 即可（一处）。
4. **§5 彩蛋**：`EGG_PULL_DP = 16`（约 47px @density 2.9688）为触发阈值；
   若觉得太灵敏（正常滚动误触）可增大到 24~32dp。
5. **未发布 Release**、**未做真机验证**。若发布：LSPosed 仓库
   `Xposed-Modules-Repo/io.github.ariinyume.dlsitesoundfloat`，tag `976-2.2.4`。

## 7. 本轮踩到的 3 个坑（留档）

1. 🔴 **975 的修法本身就是最大的坑**：把「去抖」理解成「等稳定」，
   而宿主的抖动是**规律交替**、永远不稳定 ⇒ 通道被堵死。
   **教训**：去抖判据必须保证「真信号一定能通过」，否则宁可不抖。
   本轮的兜底是**离线时序模拟**（`sim_jitter.py`）—— 这类「依赖运行时序」的判据，
   静态验证无能为力，必须建可复现的时序模型来证伪。
2. 🔴 **模拟脚本的测试序列必须体现「首次读数会种基线」**：
   第一拍就给新值 ⇒ `last == null` 分支只种基线、不产生变化 ⇒ 测出来的是
   「从零开始」而不是「换轨」，B/C 两组会**全体假 FAIL**（本轮真的踩了，4 条）。
3. 🔴 **aapt2 用枚举值打印特殊常量**：`layout_width="match_parent"` 打印成 `-1`、
   `wrap_content` 打印成 `-2` ⇒ 判据要认 `-1`，不能只认字面量 `match_parent`（本轮假 FAIL 1 条）。
4. 🔴 **取「最后一个带 id 的 View」要排除兄弟节点**：底栏 `bottom_bar` 是 CoordinatorLayout 的
   兄弟，文档顺序里排在 NestedScrollView 之后 ⇒ 直接取末位会读到 `save_button`（本轮假 FAIL 1 条）。
   正确口径是「排在 `card_misc` 之后、`bottom_bar` 之前」。
