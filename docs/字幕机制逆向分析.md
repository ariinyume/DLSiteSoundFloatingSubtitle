# DLsiteSound 2.18.0 — 字幕读取与显示机制 逆向分析报告

> 目标文件：`DLsiteSound_2.18.0.apks`（60.4 MB）
> 分析日期：2026-09-10
> 分析方式：静态分析（解包 → Hermes 字节码反编译 → 字符串表交叉引用）

---

## 0. 一句话结论

**它压根不解析 `.vtt` 文件。**

App 拿到的只是一个「字幕文件名」，然后把文件名里的 `vtt` 换成 `json`，去服务端 `optimized/` 目录请求一份**已经被服务端解析成 JSON 的字幕数据**。客户端只做三件事：下载 JSON、按当前播放秒数线性查找命中的那一条、把里面的字符串数组渲染成几行 `<Text>`。

WebVTT 的实际解析工作在服务端完成，客户端连 `WEBVITT` 魔术头和 `-->` 时间轴分隔符都没有——我在整个 22 MB bundle 里搜过，**零命中**，这是最初的关键线索。

## 1. 技术栈识别（先走对路）

拆包后第一件事就是发现：这**不是**原生 Android 应用。

| 证据 | 含义 |
|---|---|
| `libhermesvm.so` (2.1 MB) | Hermes JS 引擎 |
| `libreactnative.so` (6.2 MB) | React Native |
| `libexpo-modules-core.so` | Expo |
| `librealm.so` (9.4 MB) | Realm 本地数据库 |
| `librnskia.so` (11.2 MB) | react-native-skia |
| `assets/index.android.bundle` (22.1 MB) | 业务逻辑全在这里 |

`assets/app.config` 进一步确认：

```
Expo SDK 55 · version 2.18.0 · jp.co.eisys.dlsitesound
plugins: expo-audio, expo-video, expo-router, firebase, datadog
SOUND_RESOURCE_URL : https://content.dlsound.jp
PLAYBACK_URL       : https://playback.dlsound.jp
SOUND_SERVER_URL   : https://api.dlsound.jp
```

结论：**5 个 classes.dex 全是 RN/Expo 胶水层，逆向它们毫无意义**。真正的逻辑在 Hermes 字节码里。

文件头 `c6 1f bc 03 c1 03 19 1f`，version 字段 = **96**。
解析结果：**59,853 个函数，83,325 条字符串**。

## 2. 完整数据流

```
① 作品详情 API   GET /api/sound/v3/work/{workno}
        ↓  file.playfile.audio.vtt   ← 字幕文件名（仅文件名，不是内容）
② AudioPlayerInner 组装参数 → useSubtitles({...})
        ↓
③ loadVttData()  download(workno, 'optimized/' + vttPath.replace('vtt','json'))
        ↓  res.data.webvtt  ← Cue 数组（服务端已解析好的 JSON）
④ setVttInfo(webvtt) + setHasSubtitles(true) + setVisibleSubtitles(true)
        ↓
⑤ useMemo: 按 Math.floor(currentPosition) 线性 findIndex 命中区间
        ↓  cue.subtitles  ← string[]
⑥ <SubtitleDisplay> → currentSubtitles.map(line => <Text>{line}</Text>)
```

## 3. 关键函数逐个击破

定位方式：按函数名建索引后，字幕相关的一共只有 5 个命名函数，且 fid 全部聚集在 `58323–58763`，正是应用自身代码段。

| fid | 函数名 | 字节码大小 |
|---|---|---|
| 58323 | `useSubtitles` | 核心 Hook |
| 58337 | `parseCueTime` | 80 B |
| 58603 | `SubtitleDisplay` | 145 B |
| 58763 | `isSubtitleCapablePlayerType` | 35 B |
| 58597 | `PlayerHeader`（含 CC 按钮） | 1235 B |

### 3.1 时间解析 `parseCueTime`

```js
function parseCueTime(t) {
  return new Date('1970-01-01T' + t + 'Z').getTime() / 1000;
}
```

用 `Date` 解析器当时间码解析器。省事，但**代价是硬约束**：

- 必须是 `HH:MM:SS.mmm`。WebVTT 合法的短格式 `MM:SS.mmm` → `NaN`。
- `>= 24:00:00` 会溢出到"第二天"，逻辑失效。

反推：服务端下发的 JSON 时间戳**一定**已被规范化成三段式。

### 3.2 播放器类型闸门

```js
function isSubtitleCapablePlayerType(t) {
  return t !== 'local' && t !== 'guest' && t !== 'localClipPlaylist';
}
```

**本地文件、游客模式、本地剪辑列表 —— 一律没有字幕。**

### 3.3 网络请求（本次分析的核心发现）

```js
const res = await download(workno, 'optimized/' + vttPath.replace('vtt', 'json'));
const webvtt = res?.data?.webvtt;
```

`vttPath.replace('vtt', 'json')` —— `String.replace` 传字符串时**只替换第一处**。
若路径中别处出现 `vtt`（如目录名 `vtt/`），会替换错位置。属于潜在脆弱点，不过在受控的服务端命名下不会触发。

### 3.4 当前时刻 Cue 查找

```js
const pos = Math.floor(currentPosition);
const idx = vttInfo.findIndex(cue =>
  pos <= Math.floor(parseCueTime(cue.end_time)) &&
  pos >= Math.floor(parseCueTime(cue.start_time))
);
return idx < 0 ? [] : vttInfo[idx].subtitles;
```

三个设计取舍：
1. **秒级取整** —— 起止时间和播放位置双双 `Math.floor`。亚秒级精度直接丢弃，短于 1 秒的 cue 可能永远显示不出来。
2. **线性扫描** —— 每次播放进度更新都 `findIndex` 全表。没有二分、没有游标缓存。
3. **只取首个命中** —— 时间区间重叠时，后面的 cue 被静默丢弃。

### 3.5 竞态与缓存

`useSubtitles` 里有两个 ref，设计得挺干净：

- `requestIdRef` —— 自增序号。异步返回后比对 `reqId !== requestIdRef.current` 则丢弃结果，防止快速切歌导致旧数据覆盖新数据。
- `loadedWorknoRef` —— 记录已加载数据对应的作品号。详情重新加载时，若还是同一作品就**只清 cue 数组、保留 CC 开关状态**；换了作品才整体复位。

### 3.6 渲染

```jsx
if (!hasSubtitles || !visibleSubtitles || currentSubtitles.length === 0) return null;
<View style={container}><View style={frame}>
  {currentSubtitles.map((line, i) => <Text style={text} key={i}>{line}</Text>)}
</View></View>
```

`React.memo` 包裹。样式（从字节码反汇编还原）：

```js
container: { width:'100%', position:'absolute', bottom:theme['space/0'],
             alignItems:'center', pointerEvents:'none' }
frame:     { width:'100%', backgroundColor:'#3A3968E5', borderRadius:0,
             paddingHorizontal:theme['space/12'], paddingVertical:theme['space/8'] }
text:      { ...theme['body/regular/medium'],
             color:theme['background/on_background'], textAlign:'center' }
```

`pointerEvents:'none'` 是必需的 —— 字幕条盖在手势区上方，不能拦截双击快进。

### 3.7 CC 开关按钮

`PlayerHeader` 中，`testID = PLAYER.SUBTITLE_BUTTON`，图标 `faSubtitles`，
颜色：开启 → `theme['background/on_background']`，关闭 → `#C387E880`（半透明紫）。

## 4. 服务端数据契约（由代码路径反推）

```
GET  https://content.dlsound.jp/…/{workno}/optimized/{name}.json
```

```json
{
  "data": {
    "webvtt": [
      {
        "start_time": "00:00:03.500",
        "end_time":   "00:00:07.200",
        "subtitles":  ["第一行台词", "第二行台词"]
      }
    ]
  }
}
```

`subtitles` 是**纯字符串数组** —— 这点由 `SubtitleDisplay` 里 `{children: line}` 直接把元素塞进 `<Text>` 确认，没有任何字段解构。所以 WebVTT 的样式/定位/说话人标签等信息，在服务端预处理阶段就已经被丢弃了。

同一 API 节点还给出：
```js
track.length            = file.playfile.audio.optimized.length
track.optimizedHashname = file.playfile.audio.optimized.name
track.hasSubtitles      = !!file.playfile.audio.vtt
```

## 5. 值得注意的行为特征

| 观察 | 说明 |
|---|---|
| **字幕必须联网** | `loadVttData` 开头就检查 `isConnected`，为 false 直接清空。即使音频已离线下载，字幕仍需联网获取。App 内那句提示 "Enjoy a smoother experience with subtitled tracks by downloading them first." 说的是音频预下载，不含字幕。 |
| **有字幕就默认打开** | 加载成功后 `setVisibleSubtitles(true)`，不读取用户上次的偏好。切歌后又会被重置为默认开。 |
| **秒级精度** | 双 `Math.floor`，亚秒 cue 会丢。 |
| **无预加载/无缓存层** | 每次切歌都重新走一次网络请求，没看到内存或磁盘缓存。 |
| **Cue 查找 O(n)** | 长音频（DLsite 语音作品常见 1–3 小时）cue 数量大时，每帧进度更新都全表扫描。 |

### 安全侧顺带一提

`assets/app.config` 里明文放着 `LOGIN_PORTAL_CLIENT_SECRET`（已在本报告中省略）以及 Datadog client token。这是 Expo `extra` 字段的通病 —— 打进包里就等于公开。属于本次分析的附带观察，与字幕功能无关。

## 6. 分析方法复盘（可复用）

原始诉求是"逆向这个 APK"，但直接上 jadx 反编译 dex 会**完全跑偏**——RN 应用的 Java 层什么业务逻辑都没有。有效路径是：

1. **先看 `lib/*.so` 判断技术栈**。看到 `libhermesvm.so` 就该立刻转向 JS bundle。
2. **验证 bundle 是否为 Hermes 字节码**：文件头 `c6 1f bc 03`，紧随其后 4 字节是版本号。
3. **别全量反编译**。22 MB 字节码 → 纯 Python 反编译会产出几百 MB 且极慢（我第一次尝试就被截断在 6.9 MB / 5472 个函数）。
4. **正确姿势**：`HBCReader` 解析函数表 → `strings[fh.functionName]` 建函数名索引 → 关键词过滤 → 只对命中的 fid 调 `decompile_function`。59,853 个函数里真正要看的只有 6 个。
5. **交叉引用补盲**：反编译器丢失了属性名归属时，扫全量字节码里 `LoadConstString*` 的 arg2 和 `*ById*` 的 arg4，比对字符串表索引，即可定位"谁引用了 `vttPath`"。全量扫描仅需 5 秒。
6. **反汇编兜底**：`StyleSheet.create` 里的对象字面量走 `NewObjectWithBufferLong`，反编译器还原不出来，但反汇编注释里直接带 `# Object: {...}`。

### 踩过的坑

- `nohup cmd &` 在 Git Bash 里不能真正脱离，父 shell 退出即被杀 → 输出静默截断。
- hermes-dec 的 `HBCReader` **依赖文件句柄常驻**。`read_whole_file()` 之后若 `with` 块结束导致文件关闭，反编译会报 `ValueError: seek of closed file`。
- `start_time`/`end_time` 这两个字段名在 App 里被**两套无关功能**复用：字幕 cue（fid 58325）和音声クリップ（fid 41129 / 53193）。差点误判。
