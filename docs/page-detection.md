# 页面判定与响应机制（核心逻辑）

> 📦 本文档原为 README 的第二节，为保持首页简洁而拆出。
> ⚠️ 这是本项目**最容易改坏**的部分（同一个 bug 复发过多次），改动前请先读完本文与
> `SubtitleViewHook` 的类注释。

---

## 三态判定：**"扫不到滑条" ≠ "不是播放页"**

扫描器每轮在视图树里找"宽滑条"（宽度 ≥ 45% 屏宽的原生 `SeekBar` 家族），据此给出三种结论：

| 结论 | 触发条件 | 动作 |
| --- | --- | --- |
| `PAGE_PLAYER` | 找到**主滑条**（纵向 ≤ 82% 屏高，**且**与时间文本配对成功） | 立即显示按钮 |
| `PAGE_OTHER` | 只找到**底部 mini-player 滑条**（纵向 > 82%） | 隐藏按钮 |
| `PAGE_UNKNOWN` | 一条宽滑条都没扫到（首页、转场、被回收） | **不改变现状**，交给「锚点」判断 |

> ⚠️ **作用域仅限「按钮」**：三态判定只驱动**播放页开关按钮**的显隐，**悬浮窗不随页面判定变动**。
> 窗口只由三类事件改变：① 用户手动开关（点按钮 / 点 ✕）；② 切到**无字幕**音轨（3s 宽限后关窗）；
> ③ **播放结束**（`STATE_ENDED`，v29 起自动关窗）。离开播放页**不会**关掉悬浮窗。

关键点：

- **首页等页面根本没有 SeekBar** → `UNKNOWN`。若把"没证据"直接当"非播放页"，播放页上滑条被回收的瞬间就会把按钮闪掉。
- **列表页 / 首页底部的 mini-player 里也有同宽滑条**，与播放页主滑条**只靠纵向位置区分**。

## 播放页锚点（`anchorRef`）

判定到 `PAGE_PLAYER` 时，顺手记住主滑条所属的**页面级祖先容器**（弱引用）：

- 滑条扫不到、但**锚点容器仍真实可见** → 还在播放页（只是控制条被回收）→ **保持显示**；
- 锚点**消失 / 不可见 / 被卸载** → 确实离开了 → 隐藏。

锚点存活要求"仍挂在窗口 + VISIBLE + 有尺寸 + 祖先链累计 alpha ≥ 0.05 + 可见面积 ≥ 50%"。

> ⚠️ RN 切页动画期间页面容器会**瞬时不可见**（"假死"），所以锚点失效**不能立刻**隐藏。
> v30 起判定口径是「**墙钟持续 600ms**（`ANCHOR_DEAD_MIN_MS`）+ 最少 2 次采样」，
> 不再用「连续 N 次采样」（采样相位会让同一事件差 300ms）。
> 假死的**实测上限 1.326s**（2026-09-11T18:28:25.9：整页滑出、又滑回同一首歌同一条字幕，
> 当时按钮白闪 720ms）—— 所以 600ms 已经贴在安全边界上，**再短就会误闪**。

## 三道证据门（v26 新增，专治过渡期误判）

**问题**：播放页**入场**时页面从屏幕底部滑入，它的主滑条会一路扫过整个下半屏，途中必然穿过 82% 那条绝对位置判据线，被误判成"mini-player 滑条"→ 按钮被误隐藏；**退场**时更极端，`bottom=y=2759(99%)` 的滑条**依然完整在屏内**，纯纵坐标根本拦不住。

**修法**（判据不再依赖"绝对纵坐标"）：

1. **页面容器可见面积门** `PAGE_CONTAINER_MIN_VISIBLE_RATIO = 0.6`
   滑条所属页面容器必须在屏上占比 ≥60%（静止态实测 ≈92%~100%，过渡态掉到 ~20%~35%）。
   **与滑条位置无关**，故比 82% 稳健得多。

2. **主滑条必须与时间文本配对** `MAIN_SLIDER_TIME_LABEL_DY_DP = 80`
   播放页主滑条**下沿同排**恒有 `04:48` / `-13:34` 两个时间文本，mini-player 进度条旁一个都没有。
   配不上就不敢判 `PLAYER`（返回 `UNKNOWN` 交给锚点），**绝不因为"配不上"就判成 OTHER**。

3. **OTHER 去抖** `HIDE_ON_OTHER_STREAK = 2` + `HIDE_ON_OTHER_PROOF_MS = 250`
   单帧假阳性不再能把按钮打掉。

## 显隐延迟拆解（v30 实测口径）

把「离开播放页 → 按钮消失」拆成两段，才知道该优化哪一段（work_diag_15，v28 日志 10 次隐藏）：

| 段 | v28 实测 | 根因 | v30 修法 |
| --- | --- | --- | --- |
| ① 页面已经走了 → **我们发现** | **190 ~ 802ms** | 稳定态心跳 600ms，而 RN 转场是 translate/opacity 驱动、**不触发布局回调**，那段只能等心跳 | 廉价**锚点探针** 120ms（`ANCHOR_WATCH_MS`），只查锚点一个 View → ≤130ms |
| ② 发现死亡 → **真的隐藏** | **605 ~ 896ms** | 确认窗写成「4 次采样」：落在节流(150ms)上就快、落在心跳(200ms)上就慢 | 改**墙钟** 600ms + 最少 2 次采样 → 收敛到 600~660ms |

> **正面证据优先于负面推断**：若近期（`OTHER_EVIDENCE_TTL_MS = 400ms`）见过 mini-player 滑条，
> 且按钮**当前可见**，确认窗缩到 `ANCHOR_DEAD_WITH_EVIDENCE_MS = 200ms`，并从**最早的离开信号**起算。
> 依据：v28 日志里 `verdict=OTHER` 共 8 次，**7 次发生在按钮可见时且 7/7 都是真的离开**；
> 唯一 1 次假阳性（播放页入场动画）发生在**按钮已隐藏**时 → 隐藏本就是 no-op。
> 用「有效期」而不是「连续两次」是因为真实转场里滑条会 **OTHER → UNKNOWN 交替**，连续判定永远凑不齐。

⚠️ **没动的地方**：`HIDE_ON_OTHER_STREAK` / `HIDE_ON_OTHER_PROOF_MS` / `ANCHOR_DEAD_MIN_MS` 的安全下限都保持原值。
本轮只砍「发现得晚」与「采样抖动」，**没有**下调安全余量。

## v34：从「轮询」改成「宿主事件驱动」

v30 把段 ① 压到 ≤130ms，但那是靠 **120ms 的廉价探针**（本质仍是轮询），
而且探针只在**按钮可见**时工作 —— 按钮隐藏时唯一采样来源还是 600ms 心跳。
实测 hide → show 间隔仍有 **0.66 ~ 3.84s**（期间无任何判定日志）。

v34 换了思路：**别再「问」，让宿主自己「说」。**

钩住宿主视图树的**结构事件入口**（`hook/StructureWatcher.java`）：

| 钩子 | 覆盖的场景 |
| --- | --- |
| `ViewGroup.addView(View, int)` | 页面（子树）挂载 —— **进播放页的主信号** |
| `ViewGroup.removeView(View)` / `removeViewAt(int)` / `removeAllViews()` | 页面卸载 |
| `View.setVisibility(int)` | RN 复用页面时的 `display:none` 切换 |
| `View.setTranslationX/Y(float)` | **RN 转场的位移驱动**（← 最关键，v25/v30 反复踩过"转场不触发布局回调"） |
| `View.setAlpha(float)` | RN 转场的淡入淡出 |

事件一到就立刻跑一次完整扫描，绕过节流。成本有两道闸：
`POKE_MIN_INTERVAL_MS = 50ms` 合并同一批事件；`POKE_MAX_PER_SEC = 12` 令牌桶硬性封顶，
**防止 App 里任何持续动画把整树扫描变成常态**。

> 决策逻辑**一行没改** —— 结构事件只负责「让判定早一点跑」，所有结论仍然只由
> `detectAndLayout` 一处产出（避免两套状态机各说各话）。

另新增一条**硬证据**：给锚点挂 `OnAttachStateChangeListener`，
锚点被**从窗口摘除**（视图都没了）→ 跳过 `ANCHOR_DEAD_MIN_MS` 确认窗直接隐藏。
确认窗本来只为吃「假死又滑回来」（实测 1.326s 那次），而视图摘除不会滑回来。

### ⛔ 为什么按钮**不能**直接注入宿主控件行

需求方向原本是「把按钮塞进播放器传输控件行，跟播放键同一排，靠挂载/销毁天然零延迟」。
1.20.9 特意打了一次真实视图树 dump 去验证，结论是**技术上不可行**：

- RN 的 `ReactViewGroup` 在 `onInterceptTouchEvent()` 里**无条件拦截**触摸；
  它用 `JSTouchDispatcher` 自己重做命中测试，**只认带 React tag 的视图**。
  任何塞进去的原生 View **收不到点击** → 按钮会变成纯装饰。
- RN 的布局由 Yoga 直接 `view.layout(...)` 完成，`ViewGroup` 不参与子视图定位 ——
  外来子 View 需要我们自己摆位，且随时可能被 RN 的 `manageChildren` 清掉。

⇒ 按钮继续留在 `DecorView`（**可点击、可拖拽**），只把「什么时候显示」交给宿主事件。

> 📌 dump 的深度上限曾是 8，而 RN 真正的内容从深度 **9** 才开始（最后一行停在第二个
> `SafeAreaProvider`）。v34 已改成 22 —— 下次需要看结构时才拿得到东西。

## v35：按钮跟随页面位移（「跟手」）

**现象**（2026-09-14 录屏 + 日志，`work_diag_20`）：播放页被按住上滑时整层沿 y 平移，
逐帧测出主滑条 y 在 **1799 ↔ 2224** 之间摆动（摆幅 ≈425px，峰值位移 ≈560px），
而按钮纹丝不动 —— 看起来像「按钮没长在播放器上」。

**参考点**＝中间的**播放键**。真实结构（视图树 dump）：

```
ReactViewGroup @0,141 1272x2583 kids=19      ← 页面锚点 sPlayerAnchor
  ReactViewGroup @529,2121 214x214           ← 播放键外圈光晕
  ReactViewGroup @562,2154 148x149           ← 播放键容器
    LottieAnimationView @562,2154 148x149    ← ← 参考点（播放/暂停图标）
```

- 识别：锚点下 **≤3 层**找类名含 `LottieAnimationView` + 边长 ≥48px + 基本方正，多个取**最靠屏幕中线**的；
- 退化：找不到就退回用**页面锚点**（同一个位移层，位移量完全等价）；
- 写入：`setTranslationY(delta)` —— **不 `requestLayout`**，因此不可能形成布局回环。

### ⚠️ 与 v31 那次失败的区分（很容易被误当成回滚）

| | v31（已撤销） | v35 → v37（现行） |
| --- | --- | --- |
| 位置来源 | 主滑条几何**实时推导**，是位置**唯一**来源 | 静止位置仍是常量，只叠加**相对位移** |
| 位移来源 | ——（位置实时算） | v35/v36：基线 + 屏幕 y；**v37：transform 累加（无基线）** |
| 重算时机 | 只在扫描时（节流 150ms / 心跳 200~600ms）→ 一格格跳 | **每帧**（`Choreographer`）→ 跟手 |
| 写入方式 | `setLayoutParams` → `requestLayout` → **布局回环** | `setTranslationY` → 不触发布局 |
| 静止态 | 位置随页面滚动而变（被污染） | 位移恒为 **0**，与 v32 口径**完全等价** |

### 三个防坑点（每条都对应一个会让效果崩掉的坑）

1. **启动门**（`maybeStartPageFollow`）：结构事件到达时只读**一次**坐标判断「页面动没动」，
   动了才拉起跟帧循环 —— 否则 App 里任何常驻动画（缓冲转圈）都会把循环反复重启，白烧 CPU。
2. **基线只在真静止时采**（`captureFollowBaseline`）：三条件同时满足才落定，
   且**连续两次读数一致**才算静止。
   - 不这么做的话，播放页**入场动画期**采到的基线会让按钮此后一直偏几十 px；
   - 拖动刚开始那 50ms（跟帧循环还没起来）的一次 PLAYER 扫描会把「拖到一半的位置」
     当成新基线，位移随即归零，表现成「拖不动 / 拽到一半又弹回去」。
   > ⚠️ 这个「门③」在 v35 里**读错了字段、实际是坏的** —— 见下面 v36 节。
3. **拖动抑制门**（`PAGE_HOLD_PX`）：页面被拖开 → 不采信 OTHER 证据。
   拖动时下层列表页会从缝里露出来，它那条底部 mini-player 滑条会被当成
   “已离开播放页”的正面证据 —— 实测 2.4s 的上下拖动里连出 **6 次 `verdict=OTHER`（275ms）**，
   直接越过 `HIDE_ON_OTHER_PROOF_MS` 的 250ms 判隐藏线，按钮当场消失。
   > v36 去掉了对 `isPlayerAnchorAlive()` 的依赖（拖动期间那条判据频繁为 false）。

## v36：跟手三处致命缺陷修复

**反馈**（2026-09-14 22:25，10.7s 录屏 + 日志 → `work_diag_21/`）：
「悬浮窗会卡在屏幕边缘不跟随页面继续向下滑动，甚至有时还卡在原位置不动」

**v35 的实际运行数据**（先把事实摆清楚）：
- `page follow` 共 34 行，**全部** `ref=anchor` —— 播放键一次都没被认出来；
- 记录到的位移是 7~264px，而同一时段主滑条 y 从 **1799 → 2784**（位移 ≈985px）；
- 拖动期间每 55ms 一次 PLAYER 扫描，`button hidden (bottom mini-player #6)` 真实发生了。

三个**互相独立**的缺陷，逐条对上她的两种描述：

| # | 症状 | 根因 | 修法 |
| --- | --- | --- | --- |
| ① | **卡在屏幕边缘** | `clampFollowOffset` 按屏高比例钳制**位移量**：往下只给 `0.10 × 2772 ≈ 277px`，而页面能拖走 985px → 跟到 277px 就撞线。日志里那批 261/264px 正是撞线记录 | 改成钳制**屏幕位置**：按钮本体还在窗口内就放行，「跟到头」由屏幕物理边界决定 |
| ② | **卡在原位置不动** | `captureFollowBaseline` 的门③ 读的是 `sPlayBtnBaseY`，而播放键从没被认出来、该字段恒为哨兵值 → **门③ 永远不生效** → 拖动中每 55ms 的 PLAYER 扫描都把「拖到一半的位置」写成新基线 → delta 归零、按钮弹回，此后永远认为「这就是静止位」 | 基线收敛成唯一一份 `sFollowBaseY`（与当前参考点一一对应），门才拦得住 |
| ③ | **偶尔彻底不动** | `doFrame` 读到 `FOLLOW_NO_BASELINE` 直接 `return`、`again` 保持 false → 循环**一次性结束**。而 RN 拖动是 translate 驱动、不触发布局回调，结构事件不一定再来 → 循环再也起不来 | 只跳过该帧；连续 `FOLLOW_MISS_MAX_FRAMES`（90 帧 ≈1.5s）读不到才认输 |

**三处连带修正**：

- **参考点粘性**（`ensureFollowRef`）：v35 每次调用都现场重挑参考点，verdict 一跳就换来源、
  基线跟着漂。现在认下一个 View 实例就一直用它，只有它真的 detached / 不可见 / 尺寸归零才重挑。
- **播放键扫描够不着**（`scanPlayButton`）：v35 深度限 3、节点预算 80，而锚点有 **19 个直接子节点**
  （页面区块）、播放键在**最后一个**区块里 —— 正序 DFS 还没走到就耗尽预算了。
  v36：深度 8 + 预算 2000 + **从后往前**遍历。
- **OTHER 抑制门去依赖**：见上面第 3 条。

| 参数（v36） | 值 | 说明 |
| --- | --- | --- |
| 跟随死区 | 6px | `FOLLOW_DEADZONE_PX` |
| 静止帧数 | 12 帧（≈200ms） | `FOLLOW_STILL_FRAMES` → 之后自动注销，**空闲零成本** |
| 单次上限 | 20000ms | `FOLLOW_MAX_MS`（安全网；v35 是 6000） |
| 读失败容忍 | 90 帧（≈1.5s） | `FOLLOW_MISS_MAX_FRAMES` |
| 位移钳制 | **窗口内位置钳制** | 顶 `windowTop+8dp`、底 `windowBottom-btnH-8dp` |
| 拖动抑制门 | 24px | `PAGE_HOLD_PX` |
| 播放键扫描 | 深度 8 / 预算 2000 / 逆序 | `PLAY_BTN_MAX_DEPTH` / `PLAY_BTN_MAX_NODES` |

诊断行（v36 升级）：`page follow on:` 改成**位移每变化 64px 补一行**，并带上 `base=` / `btnBase=`；
读不到基线时补一行 `page follow skipped: no settled baseline yet`（1s 节流）——
v35 这里是**静默失败**，页面明明在动、循环就是起不来，日志里一个字都没有。

> ⚠️ **教训**：v35 那三个坑有共同点 —— 都是「**判据/诊断读的不是当前生效的那份状态**」。
> `sPlayBtnBaseY` 在退化路径下永远不写、参考点每帧重挑、钳制用屏高比例而不是真实按钮位置。
> **加新判据前先问一句：这个量在退化路径上有没有被更新？**
> 否则判据在正常路径上看起来完全正确，一退化就静默失效。

## v37：跟手换成「无基线」位移通道 + 放行 1:1 跟随

**反馈**（2026-09-14 22:44，13.4s 录屏 + 日志 → `work_diag_22/`）：
「还是之前的问题没解决：悬浮窗会卡在屏幕边缘不跟随页面继续向下滑动，
甚至有时还卡在原位置不动**或者飞到屏幕上方去了**」

### 先把 v36 的实测数据摆出来（逐帧互相关 + 「悬浮关」模板匹配）

| 观察 | 数值 | 说明 |
| --- | --- | --- |
| 每次拖动的位移上限 | **+262 屏幕 px**，一次不差 | 录屏里按钮下移 121 video px（= 262 屏幕 px）后**停在同一位置**，13.4s 内重复 6 次 |
| 262 是怎么来的 | `2772 − 103(按钮高) − 22(8dp 边距) − 2385(按钮静止 y) = 262` | **严丝合缝等于 v36 那道「窗口内位置钳制」** → 钳制本身就是「卡在屏幕边缘」的成因 |
| 基线值出现两种 | `base=2156` 与 `base=141` | 2156 ≈ **播放键**的位置（`LottieAnimationView @2154`）；141 = **页面锚点**的位置 → **参考点换人了** |
| 由它算出的位移 | `translationY=-2015px` | 2156 − 141 = 2015 → 按钮瞬间飞到屏幕上方（**她说的「飞到屏幕上方」就是这一行**） |
| `page follow skipped` | **15 次** | 那段时间按钮一步都不跟（**「卡在原位置不动」**） |

### 根因

| # | 症状 | 根因 |
| --- | --- | --- |
| ① | **飞到屏幕上方** | 参考点在「播放键 ↔ 页面锚点」之间**悄悄换人**，而基线还是旧参考点的 → 两者屏幕 y 差 2000+ px，位移瞬间变成 −2015。日志上的 `ref=` 读的是**刚刚被重置的标志位**，所以永远显示 `ref=anchor`，把「播放键其实被认出来过」完全盖住了 |
| ② | **卡在屏幕边缘** | 「必须留在屏幕内」这个**前提本身是错的** —— 按钮静止位就在屏幕下方，往下只剩 262px；而页面能被拖走 2000+px |
| ③ | **卡在原位置不动** | ① 基线只能靠「页面真的静止 2 次扫描」采到，拖动中最缺的就是它；② hide 会顺手扔掉基线，而拖动中 hide 频繁发生；③ 那道「页面被拖住」的抑制门**要用基线算位移**，没基线时直接放行 = 等于没拦 |

### 修法：把「基线」这个概念从主路径上删掉

核心是新增**无基线位移通道** `pageVisualOffset()`：

```
位移 = Σ(参考点及其祖先的 translationY) − Σ(祖先的 scrollY)
```

页面处在**布局静止位**时它恒为 0，于是：

- **不需要基线** → 「基线被覆盖 / 过期 / 与参考点不匹配」三类坑一次性消失；
- **不受参考点换实例影响** → 播放键与页面锚点算出来**完全相等**（同一祖先链，只多几个零位移节点），换人不跳变；
- 手指按住页面停在半路时它**仍是「被拖开的量」**，不会像基线方案那样自愈成 0（自愈 = 按钮弹回原位）。

祖先链上若有一条**常驻**的非零 translationY（系统 insets、宿主布局补偿），累加值会带常数偏置
→ 按钮永久偏移。所以在「确认页面静止」的那一刻标定一次 `sVisualBias = 累加值`，把它抹平。

兜底：如果这条通道在整个进程里**一次都没动过**（说明这个 App 的位移不是 transform 驱动），
自动退回老的「基线 + 屏幕 y」通道 —— 两条路都留着，不会「新通道失效 = 功能全废」。

### 三处配套

| 位置 | v36 | v37 |
| --- | --- | --- |
| `clampFollowOffset` | 钳到窗口内（往下只有 262px） | **删掉**「必须留在屏幕内」，只留 ±1.6 屏高挡异常值 → 页面移出屏幕按钮就跟着移出，页面回来按钮自然回来 |
| `stopPageFollow(true)` | 顺手**作废基线** | 只清零位移，**不动基线**；真正的作废收敛到 `invalidateFollow()`（只在参考点没了 / 换页 / 重建按钮时调） |
| 参考点换实例 | 直接改认新人，基线不动 → **-2015px 跳变** | `adoptFollowRef()` **平移基线**（`新基线 = 新参考点当前 y − 当前位移`），视觉零跳变 |
| `isPageHeld()` | 用基线算位移（没基线就放行）；且**只接在 OTHER 分支** | 无基线判据（位移 + 「刚刚还在动」时间窗 + 锚点面积下限），**同时接在「无播放页证据 → hide」那条路上**（实测 hide 正是从那条路来的） |
| 播放键 DFS | 每次参考点失效都重扫 | 加 `PLAY_BTN_RESCAN_MS=3000` 节流；扫描空窗期直接用锚点顶着 |

| 参数（v37） | 值 | 说明 |
| --- | --- | --- |
| 位移硬上限 | ±1.6 屏高 | `FOLLOW_SANITY_RATIO`，只挡异常值 |
| 「页面在动」保持窗 | 200ms | `PAGE_MOTION_HOLD_MS` |
| 「被拖开」锚点面积下限 | 12% | `PAGE_HOLD_MIN_AREA` |
| 「被拖开」位移门限 | 24px | `PAGE_HOLD_PX` |
| 播放键重扫间隔 | 3000ms | `PLAY_BTN_RESCAN_MS` |
| 跟随死区 / 静止帧 / 读失败容忍 | 6px / 12 帧 / 90 帧 | 沿用 v36 |

诊断行（v37 新增 3 条）：

- `page follow on: button translationY=…px (ref=play-button|anchor vis=… base=… ch=transform|baseline)`
- `page follow channel: transform-sum active (first motion …px, bias=…)` / `page follow bias calibrated: …px`
- `page follow rebase: ref -> play-button|anchor | base A -> B (keep offset …px)`
- `hide suppressed: page held (vis=…px ref=…)`
- `page follow skipped: no baseline & no transform channel`

> ⚠️ **教训（比技术细节更重要）**：「必须留在屏幕内」这种**未经确认的产品前提**，
> 比任何算法细节都更容易让功能看起来完全没用 —— 用户要的是「跟着页面走」，
> 而不是「跟着页面走、但别走太远」。**先问用户到底要什么，再问怎么算得准。**

## v38：治「上下滑动时按钮闪现 / 闪消失」

反馈原话（Ari 2026-09-14 23:18）：「播放页面上下滑动偶尔还是会悬浮窗按钮闪现和闪消失」。

### 数据（work_diag_23/hide_ctx.py，把每次 hide 与它之前的页面位移对上）

| 观察 | 数字 |
| --- | --- |
| 1.20.13 时段 hide 次数 | **23 次**，散布在 115 秒里 ≈ **每 5 秒闪一次** |
| 每次 hide 时页面已被拖走 | **2710 ~ 2772px**，**23/23 全中** —— 屏幕高就是 2772px |
| hide → shown 间隔 | **168 ~ 2095ms，中位 369ms** |
| 每次 hide 之前 | 都先出现过一次 `hide suppressed: page held` → **抑制门挡了一下就失守** |

### 根因：确认窗从**错误的时刻**起算

`sAnchorDeadSinceMs` 记的是「锚点**第一次**判死」的时刻，而那一刻正好是**拖动刚开始**。
从那一刻起 `ANCHOR_DEAD_MIN_MS`(600ms) 一路走完，而手指还在拖、页面还在飞 ——
按钮在半空中被判「离开播放页」而 hide，页面回弹后 331ms 又 shown。

完整现场（2026-09-14 23:16:26~27）：

```
26.740  verdict=OTHER  (主滑条消失)
26.905  anchor dead for 0ms (area=42% evidence=false need=600ms samples=1)
26.905  hide suppressed: page held (vis=1459px ref=anchor)   ← 门还在
27.014  page follow: button translationY=2768px              ← 页面到位（屏幕高 2772）
27.561  no player evidence for 709ms (anchor dead 655ms) -> hide   ← 656ms ≥ 600ms，门已失守
27.561  button hidden (player page left)
27.891  player anchor -> ReactViewGroup h2583 vis93% kids19  ← 回弹
27.892  button shown (player page)                           ← 331ms 后又亮
```

**「扫不到播放页证据」在拖动 / fling 期间是这一刻的正常现象** —— 页面被拖到看不见控件
的地方了。它不是「离开播放页」的证据。

### 修法一：确认窗改成从「页面最后一次运动」起算

```java
since = max(sAnchorDeadSinceMs, sLastPageMotionMs, ...)
```

真·离开播放页时页面也会停（离场动画 ≤300ms），确认窗随即正常推进，
最坏只比原来晚一个离场动画的时长，不会「赖着不走」。

> ⚠️ 但**光改起算点不够**：页面到位后还会**停**在那里几百毫秒才回弹（实测 hide→show
> 间隔中位 369ms、最长 2095ms），那段时间「无证据」是**真的**，确认窗照样会走完。

### 修法二（主因）：抑制门在「页面被拖到极限」时会失守 —— 补判据③「位移快照」

页面被拖走 2710~2772px 时，参考点失去「可用」资格（滚出屏幕）、锚点可见面积也趋近 0
→ `isPageHeld()` 的判据②（`|位移| ≥ 24px` **且** `面积 ≥ 12%`）**恰好在最需要它的时刻
返回 false**。日志里每次 hide 之前都先出现过一次 `hide suppressed` —— 正是「挡住了，
然后在页面到位的那一刻失守」。

| 判据 | 内容 | 拖到极限时 |
| --- | --- | --- |
| ① 刚刚还在动 | `now − sLastPageMotionMs < 200ms` | 页面一停就失效 |
| ② 当前位移 + 面积 | `\|vis\| ≥ 24px` 且 `area ≥ 12%` | **参考点滚出屏 / 面积趋 0 → 失效** |
| ③ **位移快照**（v38 新增） | `\|sHeldOffset\| ≥ 24px` 且 `now − sHeldOffsetMs < 1500ms` 且**参考点仍 attached** | **成立** → 维持原状 |

`attached` 是「被拖开」与「真离开」的**分水岭**：

- 被拖到极限 —— 参考点只是滚出屏幕，`isAttachedToWindow()` 仍为 `true` → ③ 成立，不隐藏；
- 页面被卸载（真离开）—— RN 会把容器 detach → ③ 立即失效，正常隐藏，**不会赖着不走**。

快照由 `pageVisualOffset()` 在**成功读到位移时**更新（位移 / 时刻 / 当时的参考点），
只在 `invalidateFollow()`（换页 / 参考点没了 / 按钮重建）时作废。

配套两处，让 `sLastPageMotionMs` 精确可信：

| 位置 | v37 | v38 |
| --- | --- | --- |
| 帧循环刷新时刻 | **每帧无条件**刷新 | **只在位移真的变了**才刷新（否则比页面真正停下晚 ≈200ms） |
| `notePageMotion()` 调用点 | 只有结构事件 | 结构事件 **+ 扫描心跳**（RN 的 translate 拖动不触发布局回调，结构事件不保证来） |

### 诊断行（v38 升级）：

- `anchor dead for …ms (area=…% evidence=… need=…ms samples=… still=NNms)` ——
  `still=` = **页面已静止多久**，它就是确认窗的起算基准。
- `hide suppressed: page held (vis=…px ref=… snap=…px/…ms attached=true|false)` ——
  抑制门生效，同时打出判据③的原始量。
- `no player evidence for …ms (anchor dead …ms evidence=… | snap=…px/…ms attached=… vis=…px) -> hide` ——
  **门失守时**也能一眼看出是判据②失效、还是③超期 / 参考点已 detach。

> ⚠️ **教训**：计时类判据要问「**这个钟是什么时候开始走的**」。
> 「锚点判死」和「用户离开页面」在拖动场景下差了整整一段飞行时间，
> 而这段时间里唯一可信的锚点是「页面还在动」。

## v39：治「位移闪跳」——跟帧循环**不许在页面停半路时注销**

### 症状

播放页上下拖动时按钮会**冻住几百毫秒、然后一次性补跳几百像素**。
（v38 已经把「闪消失 + 闪现」治好了：23:55:10 之后 92 秒里 28 次 `hide suppressed`、
**0 次 `button hidden (player page left)`**。所以这一版只剩「位置」的问题。）

### 实测（2026-09-14 23:55:10~23:56:33 一次连续拖动，1200+ 个跟随采样）

按「跟手重启」（`page follow on:` = 新一轮循环的第一行）统计：

| 指标 | 实测 |
| --- | --- |
| 重启次数 | 86 |
| **停顿 ≥100ms 的重启** | **86 / 86**（100%） |
| 停顿时长 p50 / p90 / max | **587ms** / 1.7s / 583s |
| 补跳量 p50 / max | **122px** / 2769px |

典型形态（原样摘录）：

```
t=86152347  停顿 554ms  上一个值 2765px  一帧跳 -337px
t=86154729  停顿 554ms  上一个值 2760px  一帧跳 -292px
t=86157277  停顿 607ms  上一个值 2740px  一帧跳 -322px
```

按钮停在 2765px（页面被拖到极限）**一动不动 554ms**，然后一帧跳到 2428px。
循环停了、页面还在动 —— 这一段就是「位移闪跳」。

### 根因

跟随是 `Choreographer` 帧循环自己续帧的（`again = true`），**不需要外部事件**；
但它的终止条件是无条件的：

```java
if (sFollowStill >= FOLLOW_STILL_FRAMES) return;   // 连续 12 帧位移没变 → 注销
```

页面被拖到极限后位移**不再变化**（恒为 2765），于是 12 帧（≈100~200ms）后循环自杀。
而重启 `maybeStartPageFollow()` 的**唯一调用点是宿主结构事件** —— RN 的回弹 /
慢速拖动**不保证**产生结构事件（translate 不触发布局回调）。结果：

```
循环停 → 页面开始回弹 → 没有事件 → 按钮冻住 → 几百毫秒后某个偶然事件唤醒 → 一帧补齐
```

> ⚠️ 这正是「把控制权交给外部事件」的代价：**续帧靠自己、重启靠别人**，
> 而「别人」在最需要的那一刻恰好沉默。

### 修法（三处，全在 `hook/ActivityButtonHook.java`）

| # | 改动 | 作用 |
| --- | --- | --- |
| ① | 帧循环里：`\|delta\| > FOLLOW_DEADZONE_PX`（页面仍被拖开）时**不走静止注销**，只靠 `FOLLOW_MAX_HELD_MS`（2min）/ MISS 上限收口 | 消掉 300~1700ms 冻结 + 几百 px 补跳（主修） |
| ② | `maybeStartPageFollow()` 增加判据：**页面此刻就是被拖开的**也直接拉起；并把它挂到 `detectAndLayout` 的 **55ms 扫描心跳**上 | 循环万一掉了，最坏 55ms 接上（安全网） |
| ③ | `showButton()` 在 `setVisibility(VISIBLE)` **之前**先 `syncFollowOffsetOnShow()` 对齐位移；显示之后再 `maybeStartPageFollow()` | 消掉「先在静止位露脸、62ms 后跳 345~448px」 |

附带：回到静止位时若残留在亚死区内就直接 `applyFollowOffset(0)` 归零 ——
v38 实测页面回位后按钮还留着 **20~107px** 的残留，而 `captureFollowBaseline()`
的「位移为 0」那道门因此永远进不去，基线再也没机会自愈。

> 成本：页面被拖开时循环每帧多跑一次「~15 个节点的 `getTranslationY`/`getScrollY`」，
> 没有布局、没有 requestLayout、没有日志。可忽略。

### 验证方法（下一轮直接量）

新日志 `page follow resume: catch-up Npx after Nms` 就是断层量。
修好后这一行应该**基本不出现**；出现的话数值应远小于 100ms / 64px。
配套脚本：`work_diag_24/restart.py`（重启断层统计）、`work_diag_24/rest.py`（静止位残留）。

## 实现细节（易踩坑）

- **幽灵滑条过滤**：候选宽滑条必须同时满足 `isShown()` + `alpha ≥ 0.05` + 横纵起点在屏内
  + 所属容器通过可见面积门 —— 否则不算"扫到了滑条"（RN 会留下已回收但仍在视图树里的 `SeekBar`）。
- **按钮重建**：必须用 `sLastDecision` 初始化新按钮的可见性（否则会先按默认值闪一下），
  并且 `sLastBtnText` 必须重置（否则文案被历史值顶住、不再更新）。
- **结构事件钩子体绝不能抛异常**：钩子挂在 `View.setAlpha` 这类**每帧都调**的方法上，
  异常会直接打到宿主。`StructureWatcher` 里统一 try/catch 吞掉。
